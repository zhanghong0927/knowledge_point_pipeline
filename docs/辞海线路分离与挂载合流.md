# 辞海线路分离与挂载合流

六个阶段和 `pipeline.py plan/check/run` 保持不变。本次仅改准入、清洗路由和挂载输入，不修改分类、抽取或清洗提示词。

## 1. 分类准入

```json
"dictionary_approval": {
  "enabled": true,
  "allowed_families": ["entry_prose"]
}
```

- 默认只接第一类词条＋连续正文。O1、O2均属于entry_prose；不重新调用模型细分一次。
- 原分类和MD证据仍须通过旧校验，不能仅凭family字符串放行。
- 已确认fixed_fields/text_commentary但未在名单中的，写入not_selected.jsonl；其他、待定及技术失败分别保存。
- 显式设置三类名单可恢复旧准入口径。空名单、未知类型、重复类型均报配置错误。
- `enabled=false`仍是旧的外部已放行书单模式，不是扩大allowed_families的开关；该模式需用户自行保证外部书单口径。
- 无准入书籍时保留报告并停止，不调用抽取模型。

## 2. 独立清洗

```text
辞海 verified/INPUT.json + source_prepared/books.json
  → v22名称格式（名称优先，仅review补少量正文）
  → v9来源学科范围
  → V46正文选择、定义分离及对应检查
  → 04_cleaning/export/records.jsonl

重要书籍
  → 原normalize/rule/model/restore
  → 独立运行目录的04_cleaning/export/records.jsonl
```

辞海原生结果位于04_cleaning/dictionary。FINAL_RECORDS、DISPOSITIONS、REVIEW、TECHNICAL_FAILURES、SUMMARY和STATE保留；原生finished_with_pending表示仍有待定/失败，不称全部成功。标准出口只接受所有层都通过的记录，保留ID、书目与位置source；trace保存原始raw_content、边界上下文及清洗结果，不作为新增知识点计数。

空定义和解释仍允许。原生清洗只允许原文片段选择与格式清理；这次接线不保证语义错误已经解决。模型服务当前须为无鉴权端点。

只执行第4步时设置paths.knowledge_input为原生已核验INPUT.json，paths.cleaning_books为匹配书单；其余API及学科配置照常填写。dictionary轨不接受standard格式替代原文证据。

调用清洗前核验每条的MD路径、文件哈希、词头与正文字符位置、raw_content和逐行上下文。无对应原文、正文不符或学科/书目身份不符时停止，不向模型提交。scope_config须存在。

INPUT所在目录须保留clean-prepare生成的MANIFEST、PREPARED及input_sha256快照证明，补充上下文一起受输入哈希约束。旧INPUT缺少此证明时，在新目录执行原生clean-prepare重新冻结；无需重跑抽取模型，也不允许手工改写快照哈希。

## 3. 第五步合流

先分别执行两条线路的01至04。为共同挂载建立新的运行目录，在同学科配置中指定：

```json
"mounting": {
  "inputs": [
    "{root}/runs/my_dictionary/04_cleaning/export/records.jsonl",
    "{root}/runs/my_important/04_cleaning/export/records.jsonl"
  ],
  "threshold": 0.85,
  "min_depth": 2,
  "max_depth": 5,
  "max_related": 2,
  "workers": 16
}
```

沿用原单学科配置结构（track仍为dictionary或important），paths.run改为新共同挂载目录；此配置只执行05、06，不运行01至04。

```bash
python pipeline.py plan --config configs/my_join.local.json --stages 05,06
python pipeline.py check --config configs/my_join.local.json --stages 05,06
python pipeline.py run --config configs/my_join.local.json --stages 05,06
```

也可直接使用已有挂载入口：

```bash
python adapters/mounting_bridge.py prepare \
  --require-cleaned \
  --input /absolute/dictionary/export/records.jsonl \
  --input /absolute/important/export/records.jsonl \
  --subject-slug mechanical_engineering \
  --taxonomy /absolute/taxonomy.json \
  --out /absolute/new_mounting_directory
```

每份输入的路径、数量和SHA256进入PREPARED.json；后续挂载、复核、导出前重新验证。缺失文件、重复输入、同学科ID冲突或跨学科输入停止并报错，不自动覆盖、去重或改ID。只有一个输入时原CLI调用仍有效；旧PREPARED格式仍可读取。

pipeline内置挂载强制核验每份records旁的report和trace，及其绑定的原生通过判定、输入和输出哈希。未清洗、待定、失败或证据被修改的数据不能混入合流。旧清洗出口没有此证明时，应在新目录重新导出；不手写通过标记。独立调用mounting_bridge不带--require-cleaned仍兼容旧输入，由调用方负责其清洗口径。limit仅限制处理条数，完整输入仍先校验ID和学科。

挂载规则、阈值、路径复核和最终同分支去重不变。多输入只支持内置mounting_bridge；自定义hook不得静默只处理一路。配置inputs省略时仍只处理本次清洗输出。

## 4. 恢复与验证边界

- 变更路由、类型名单或输入名单后使用新运行目录，不覆盖旧结果和断点。
- 原run锁、配置冻结及resume/retry-failed机制保留。
- 辞海导出核对原生终态、输入哈希、逐层通过ID集合、数量和来源；已完成出口复用时检查内容哈希。
- resume跳过第4步前重新核验清洗证明及原生文件，删除或改动STATE、DISPOSITIONS等文件不会被当作可复用的完成结果。
- 测试验证接口、原文证据保留与状态分流。离线模型fixture不等于真实服务或语义质量验收。
