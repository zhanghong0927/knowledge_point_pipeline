# 运行与断点恢复

## 先确定正在恢复哪一层

| 入口 | 适用范围 | 重要限制 |
|---|---|---|
| `pipeline.py run --resume` | 按总控跳过条件复用已完成任务；源码、输入一致由调用方保证 | 自动核对配置SHA、任务描述签名、声明产物存在性及项目资产绑定，不普遍重验内容或原生通过证明 |
| `pipeline.py run --resume --retry-failed` | 显式允许再次执行失败任务 | 不删除输出，能否恢复仍由原生模块决定 |
| `staged_benchmark.py run` | 新冻结根目录的批量全局分轮运行 | 没有通用resume参数，拒绝已有STATUS或gateway目录 |
| `recover_fullbook_v5.py` | 已核验的辞海原生抽取目录独立补跑 | 仅恢复抽取，不自动完成清洗、挂载或跨版本整次任务迁移 |
| 本轮专用404/迁移适配器 | 明确冻结任务、源码指纹和故障名单 | 不是任意旧任务的一键恢复工具；不作为仓库通用启动入口 |

```bash
python -B pipeline.py run --config configs/my_run.local.json --resume
python -B pipeline.py run --config configs/my_run.local.json --resume --retry-failed
```

只有`04.clean_dictionary`和`04.restore_trace`在跳过前额外调用清洗导出证明核验。其他已完成任务可能在同路径输入、源码或产物被原地修改后仍被跳过；`SKIP`和产物存在不等于内容核验通过。调用方必须保留并外部核对冻结源码、输入和产物指纹；无法证明一致时使用新运行目录，不能依赖`--resume`自动发现全部变化。

源码、模型、上下文、输入或资产版本变化时，先保留旧目录并准备迁移证明。新版本不能直接覆盖旧冻结code，临时索引也不能充当业务检查点。

## 接续核验顺序

1. 核对控制器、原生子进程和网关的PID及启动时钟，排除重复调度或同时写入。
2. 读取本轮STATUS、JOBS、逐书STATE、原生轮次回执、事件前缀及成功缓存，不只看总状态或PID。
3. 区分模型有效结果、格式失败、服务故障和因停机未取得模型响应的尝试。
4. 若需迁移，保留不可变旧备份，核对来源、ID、原文、配置和源码差异；成功记录及成功缓存保持不变。
5. 使用适配当前阶段的唯一恢复入口，验证新请求、新回执和实际记录推进后，才认为已接续。

服务健康和模型身份需要实际核实；固定等待时间已到、HTTP200或PID存在都不能单独证明业务恢复。临时服务故障允许暂停当前轮，完整性冲突仍须停止。

## 故障重试边界

- 挂载传输故障、JSON解析及已识别响应结构异常可进入原第二、三轮；没有额外第四轮。
- 有效的accepted、needs_review、insufficient_evidence、out_of_scope等结果不当作接口失败重试。
- 已确认注销404须依据具体记录和错误证据专项恢复，不能普遍重试所有4xx。
- 故障尝试补偿与正常轮次失败分别留痕，不删除旧失败来制造全通过。

## 完成判定

逐阶段原生回执、最终SUMMARY及去重VERIFICATION应相互对应。分类不确定与未接受均不在导出中；技术收尾可保留未解决项。技术流程结束、抽取partial和语义验收使用不同状态。
